Engine Source Documentation

Overview

The Engine is a component-based game framework developed in the D programming language with SDL2 bindings. It features a Python-based level editor built with Tkinter. The engine is designed around a mouse-and-cat themed maze game, where the player (mouse) must navigate to reach a goal while avoiding enemies (cats) and collecting points along the way.

Python TKinter Interface

Overview

The Python interface provides a complete game editor, allowing users to create and modify levels through a graphical interface rather than manual JSON editing. The interface also handles game launching and configuration settings.

Installation

To install the required dependencies, run the following command from the Engine directory:

python -m pip install -r interface/requirements.txt

Running the Interface

To start the interface, run the following command from the Engine directory:

python interface/main_menu.py

Interface Components

  • main_menu.py

    The main entry point for the interface, providing access to:

    • Play Game - Launches the D engine with the selected level
    • Level Selection - Opens the level chooser to select existing levels
    • Level Editor - Opens the level editor for creating or modifying levels
    • Options Menu - Configure audio and other game settings

  • options_menu.py

    Manages game settings by modifying the options.json file, including:

    • Music volume control (0-1000 scale for SDL_Mixer)
    • Background music selection from available .wav files
    • Generates a JSON configuration that the D engine loads at startup

  • level_chooser.py

    Provides an interface to:

    • Preview level layouts with a miniature rendering
    • Load levels for editing or playing
    • Manage level files stored in the levels/ directory

  • edit_menu.py

    Complete level editor with:

    • 32x32 grid editing with wall, player, enemy, goal, and point placement
    • Level validation to ensure playability (checks for player and goal)
    • Save/load functionality for level JSON files
    • Visual preview of game elements

  • toolbar.py

    Manages the editing tools for the level editor, including:

    • Tool selection interface (walls, player, enemies, etc.)
    • Visual indicators for the currently selected tool
    • Tool application logic for level editing

  • sprite_loader.py

    Handles image resources for the interface:

    • Loads and scales sprite images for the editor
    • Provides consistent access to game object visuals
    • Manages sprite mapping between editor and game engine

Level Editor and JSON Format

The level editor generates JSON files that bridge the Python interface and D engine. The JSON structure includes:

  • level_name: The name of the level (used for display)
  • grid: A 32x32 grid of characters representing the level layout
  • sprites: Mapping of grid characters to sprite image file paths
  • sprite_animations: Mapping of grid characters to animation metadata file paths

Grid Elements:

  • W: Wall (obstacle)
  • M: Mouse (player character, only one allowed)
  • C: Cat (enemy that chases the player)
  • G: Goal (level completion trigger, only one allowed)
  • P: Pellets/Points (collectibles that increase score)
  • (space): Empty cell (navigable path)

Interface-Engine Integration

The workflow between the Python interface and D engine works as follows:

  1. User creates/edits a level using the graphical editor
  2. Level is saved as a standardized JSON file in the levels/ directory
  3. When playing a level, the interface launches the D engine as a subprocess: dub -- Assets/level1.json Assets/options.json
  4. The D engine parses the JSON files to construct the game environment
  5. The engine loads sprites, initializes game objects, and starts the game loop

Level Validation: The editor performs several checks before saving:

  • Exactly one player (M) position
  • Exactly one goal (G) position
  • Valid 32x32 grid dimensions
  • Path connectivity between player and goal (to ensure level is solvable)

Core Engine Files

  • app.d

    The main entry point of the D application. Parses command line arguments to determine:

    • Level file path (for game content)
    • Options file path (for audio settings)
    • Initializes the GameApplication with these parameters

    Usage: dub -- Assets/level1.json Assets/options.json

  • gameapplication.d

    The core application manager that implements:

    • SDL window and renderer initialization (1280x800 resolution)
    • Resource manager initialization
    • Audio system setup with volume control based on options.json
    • Scene initialization and management via SceneTree
    • 60 FPS fixed time step game loop (with SDL_Delay for frame timing)
    • Proper resource cleanup on application termination

    The game loop implementation uses the following pattern:

    1. Input processing (SDL events)
    2. Game state update
    3. Rendering
    4. Frame timing to maintain 60 FPS

  • gameobject.d

    Implements the foundational component-based architecture with:

    • GameObject class as a container for components
    • IComponent interface with Update() and Render() methods
    • Point struct for position representation
    • SpriteComponent for visual representation and animation
    • ScriptComponent as a base for custom behavior scripts
    • BaseComponent abstract class for common component functionality
    • CollisionComponent for basic rectangle collision detection
    • AnimatedTexture struct for sprite animation with JSON metadata

    The component system allows for flexible object composition:

    • Components can be added/removed at runtime
    • Generic GetComponent<T>() method for component access
    • Component Update/Render calls are propagated from the GameObject

  • gamescene.d

    Implements the main gameplay logic:

    • Level parsing from JSON (grid layout, sprites, animations)
    • Game object initialization for player, enemies, walls, goals, and points
    • Score tracking and display with the ScoreComponent
    • Collision detection between player, enemies, and collectibles
    • Game state management (running, game over conditions)
    • Scene rendering with proper layering of game elements

    The grid system uses a 32x32 layout with:

    • 40x25 pixel cells for rendering
    • Character-based grid representation matching the JSON format
    • Separate tracking for collectible items and navigable spaces

  • menuscene.d

    A placeholder for an in-game menu system with:

    • Scene framework for menu implementation
    • State tracking for menu visibility
    • Structure for future input handling and rendering

    The MenuScene is currently minimally implemented, with most functionality handled by the Python interface instead.

  • scene.d

    Provides the scene management framework:

    • Scene base class with virtual Input/Update/Render methods
    • SceneTree class for managing multiple scenes
    • Scene switching capabilities via SetPresentScene()
    • Centralized input, update, and render dispatching

    The SceneTree implementation supports:

    • Scene collection with indexed access
    • Active scene tracking and management
    • Event propagation to the active scene only

  • audiomanager.d

    Singleton-pattern audio system that provides:

    • SDL_Mixer initialization and configuration
    • Music loading with path-based caching
    • Playback control with looping options
    • Volume adjustment (0-1000 scale)
    • Proper resource cleanup for audio assets

    The AudioManager uses:

    • 44.1 kHz sampling rate with stereo output
    • 2048 byte buffer size for audio mixing
    • Centralized music resource management to prevent duplicate loading

  • resourcemanager.d

    Singleton-pattern resource manager for texture handling:

    • BMP image loading via SDL
    • Path-based texture caching to prevent duplicate loading
    • Centralized texture creation and management
    • Error reporting for resource loading failures
    • Proper cleanup of all loaded resources

    The ResourceManager:

    • Requires initialization with a valid SDL_Renderer
    • Uses string paths as keys for texture lookup
    • Manages the full texture lifecycle from loading to destruction

  • sdl_abstraction.d

    Provides cross-platform SDL initialization:

    • Platform-specific SDL library loading (Windows, macOS, Linux)
    • SDL initialization with error reporting
    • Proper SDL shutdown on application exit
    • Module constructor/destructor pattern for automatic initialization/cleanup

    Uses bindbc.sdl for dynamic loading of SDL without static linking, supporting:

    • Windows: Explicit DLL path "SDL2.dll"
    • macOS/Linux: System-standard library locations
    • Detailed error reporting for missing libraries or symbols

  • textrenderer.d

    Implements text rendering capabilities:

    • ScoreComponent for score display in the game
    • TTF font loading and management
    • Pre-rendering of score values for performance optimization
    • Text positioning relative to the owner GameObject
    • Clean resource management for fonts and textures

    The ScoreComponent optimizes performance by:

    • Pre-generating textures for score values in increments (0 to maxScore)
    • Using texture caching to avoid repeated rendering of text
    • Supporting custom font size and color configuration

Architecture

The engine implements several key architectural patterns:

  • Component-Based Architecture: Game objects act as containers for components that define behavior and appearance
  • Singleton Resource Management: AudioManager and ResourceManager provide centralized resource handling
  • Scene Graph: SceneTree manages different game states through a collection of scenes
  • Event-Driven Input: SDL events are processed and propagated through the scene hierarchy
  • Data-Driven Level Design: JSON configuration defines level layouts and game object properties
  • Fixed Time Step Loop: Game updates at a consistent 60 FPS with frame timing

Implementation Notes

  • The engine uses BMP format for images due to SDL's built-in support, though this limits transparency options
  • Animation data is stored in separate JSON files that define frame sequences and timing
  • Collision detection uses simple rectangle-based checks without more advanced physics
  • The game uses a grid-based movement system rather than continuous pixel movement
  • The Python interface handles most of the user interaction, with the D engine focusing on gameplay

Dependencies

  • SDL2 (via bindbc.sdl) - For rendering, input, and window management
  • SDL2_mixer (via bindbc.sdl.mixer) - For audio playback
  • SDL2_ttf (via bindbc.sdl.ttf) - For text rendering
  • Phobos (Standard D library) - For core functionality (std.file, std.json, etc.)
  • Python 3.x (with Tkinter) - For the level editor interface
